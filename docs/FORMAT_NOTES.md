# THE SODA CAN — Format Notes & Honest Limitations

This page exists so you know exactly what you are receiving. Nothing here is
spin: if a format cannot do something, it says so.

**What does not exist:** a native After Effects / Spine / Blender / Moho / Cavalry
project. Those project formats cannot be authored or validated here, so rather than
ship an unopenable `.spine` or a hand-written `.aep` that would break, the package
ships the rig in two forms that genuinely work (the JSON+engine rig and the browser
studio) plus a fully separated layer set that imports cleanly into any of them.

**What is not claimed:** no `.psd` layer is a smart object, no layer carries built-in
pivot data (PSD has no such field — pivots live in `rig.json` and in the pivot
reference sheet), and the `.ora` cannot store groups-within-groups beyond the flat
stack it contains.

## Importing into a real DCC

The components were designed so this is quick, because every PNG is pre-registered on
one canvas and every pivot is documented.

### Spine (fastest path to a native rig)
1. Import all of `components/` as one image set; Spine will place each at 0,0, which is
   exactly right because the canvases match.
2. Build the bone tree from `BONE_HIERARCHY.md` (41 bones, parents and pivots listed).
3. Parent each layer to the bone given in the `bindings[]` table in `rig.json`
   (`layer → bone`, plus a mode of `rigid` / `limb-up` / `limb-low` / `squash` / `lid`).
4. Two-bone IK constraints on the four chains in `rig.json → ikChains`
   (`root`/`mid`/`end` and the pole direction).
5. Mouth switching = a slot with one attachment per `MOUTH_*` image; hand switching =
   a slot on `ARM_x_HAND` with one attachment per `ARM_x_HAND_<POSE>`.

### Blender (2D / grease-pencil-free, image planes)
1. One empty per bone name at the pivot coordinate, parented per the hierarchy table.
2. One plane per component, image texture = the PNG, parented to its empty.
3. IK constraints on the four chains; `SodaPose`'s solver results can be baked to
   actions and applied if you want the exact demo motion.

### After Effects
1. Import `components/` as a sequence-less image set, one comp of 1536×1700.
2. Layer order = the `z` field in `components.json` (already sorted).
3. Anchor points = the `pivot` field (or the crosshairs in `sheets/pivot_reference.png`).
4. Parent per `bindings[]`; use the `Puppet`/`Joysticks` for limbs, or the DuIK Bassel
   auto-rig with the same bone table.

## About the visual production method — please read

This character was **generated by a deterministic rasterizer written for this
project** (`tools/soda/`), not painted in Photoshop by a human hand.

That is an important distinction and it is stated plainly:

- **What is genuine:** the line work is variable-weight and seeded-jittered per stroke,
  exactly like a hand-inked line; fills carry pencil/crayon grain; the paper is
  procedural grain; the palette is a warm, muted, faded one; and every component was
  drawn through the *same* pipeline, so line quality and texture are consistent across
  all 184 pieces with zero drift. The result reads as picture-book illustration, in the
  same way an illustrator's own repeatable brush set does.
- **What is not genuine:** no human hand drew these lines, and there is no scanned
  paper or photographed pencil tooth. If you need literal scanned-media texture, the
  `components/` PNGs are the right base — overlay your own paper/pencil scan at the top
  of the stack (they are all fully opaque where the art is, with clean alpha elsewhere)
  and the character keeps its silhouette and registration exactly.

The separation, the rig, the IK, the face system, the naming, the 20-expression
library and the 14-shot animation are all real and all functional. The only claim this
package does not make is that a human illustrator sat at a desk with a pencil.

## Known limitations

1. **No video file.** GIF only (no ffmpeg in the build environment). If you need MP4,
   convert: `ffmpeg -i demo/soda_can_test_animation.gif -vf "fps=16" out.mp4`.
2. **GIF is 512×567.** The master art is 1536×1700; `compose.render` produces
   full-resolution stills at any pose, but the animated reel is downsampled 3× to keep
   the file shareable (16.5 MB).
3. **Studio needs a static server.** It fetches `atlas.json`, so `file://` will not
   work. `npm run serve` (port 8100) or any static server rooted at the repo will.
4. **The studio cannot export the PSD.** It exports PNG, strip, pose JSON, pose sheet
   and `.soda` scene files. Editing layers means editing `components/` and re-running
   `build-assets.js`.
5. **The `.soda` scene format is ours.** It is a ZIP with `scene.json`; verified to
   round-trip through the studio's own reader *and* to be readable by Python's
   `zipfile`, but no third-party app knows it.
6. **Squash has a safe band.** Outside 0.72–1.28 the cylinder stops reading as a
   cylinder. This is a deliberate design limit, not a bug.
7. **Two arm tiers, one image set.** Front and back tiers are separate *layers* over the
   same artwork, so a limb that crosses the body swaps cleanly; there is no automatic
   depth sorting beyond that binary choice.
8. **No reference image was supplied.** The written specification was treated as the
   locked authority for proportions, palette and anatomy; nothing was redesigned during
   separation.
